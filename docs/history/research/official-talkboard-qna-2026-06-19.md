# Multimodal 236722 공식 토크 Q&A 분석

이 문서는 Multimodal 토크 게시판의 공식 중요 게시글 4개와 댓글의 공식 답변을 작업용 기준으로 압축한 것이다. 구현, 실험, 프롬프트, 모델 선택, 제출 산출물 검증 시 이 문서를 먼저 확인한다.

## 작업 기준 요약

- 1차 평가는 Public Score가 아니라 Private Score 100% 기준이다. Public Score는 개발 참고 지표일 뿐 1차/2차 평가와 직접 관련 없다고 공식 답변이 있었다.
- Public 샘플은 오픈 벤치셋 기반이고, Private 샘플은 운영진 자체 제작 샘플을 포함한다. Public에서 텍스트만으로 높은 점수가 나와도 Private에서 같은 방식이 유효하다고 보면 안 된다.
- 이 평가는 멀티모달 QA 평가다. 이미지 정보를 무시하는 text-only 접근은 Public에서는 통할 수 있어도 공식 취지와 최종 평가 방향에 맞지 않는다.
- Public 리더보드는 제출 형식, 추론 파이프라인, 문제 이해, 오픈 벤치셋 기준 성능을 확인하는 참고 신호로만 사용한다.
- 자체 검증셋과 검증 전략이 필요하다. Public만 보고 프롬프트나 모델을 결정하면 Private/Hidden에서 흔들릴 수 있다.
- 테스트셋의 질문 유형, 선택지 패턴, 문항 구성, 표현 방식 등을 분석해 유사 학습 데이터, 예시, 프롬프트, 규칙을 만드는 것은 Data Leakage 위험이다.
- 제공된 train 샘플 1개는 학습셋이 아니라 데이터 형식과 제출 구조를 이해하기 위한 예시다. 입출력 형식을 맞추는 데 참고하는 것은 가능하지만, test 패턴을 추정해 활용하면 규칙 위반이다.
- 모델은 2026-05-31까지 공식 가중치가 공개된 오픈소스 모델만 사용한다. 원격 API 기반 추론은 금지다.
- 최종 답변은 LLM이 생성한 결과여야 한다. 단순 조건문, 다수결, 평균, 룰 기반 매핑, 사전 정의 정답 목록 선택만으로 최종 label을 결정하면 안 된다.
- 앙상블, 다중 프롬프트, 후보 생성/검토는 가능하지만, 최종 제출 답변은 LLM이 후보와 근거와 검토 결과를 종합해 생성한 것으로 남겨야 한다.
- 기준 평가 환경은 RTX A6000 48GB, Python 3.10, CUDA 12.4, PyTorch 2.6.0, Ubuntu 20.04다.
- `requirements.txt`로 vLLM, transformers, accelerate, PyTorch 등 Python 패키지 버전 조정은 가능하다. 단, 기준 환경의 Python/CUDA/OS/GPU에서 설치 및 실행 가능해야 한다.
- CUDA, OS, Python 버전, GPU 같은 기준 평가 환경 자체를 바꾸는 것은 허용되지 않는다.
- 권장 추론 시간은 test 8,500개 약 70분, hidden 1,500개 약 13분이다. 공식 답변상 단순 초과 즉시 실격은 아니지만, 실행 불가, 모델 로드 불가, 환경 재현 불가, 또는 시간 기준의 큰 초과로 정상 평가가 어렵다고 판단되면 심사 제외 또는 실격 처리될 수 있다.
- 더 빠른 추론에 대한 별도 가산점은 없다. 속도는 실격 리스크 관리와 재현성 조건으로 본다.
- 오프라인 평가 환경에서 외부 API 호출 또는 인터넷 통신 없이 실행 가능해야 한다.
- 2026-06-19 기준, "70분 기준이 순수 추론만인지, 모델 로드/이미지 로드 등 전체 추론 코드 시간을 포함하는지"에 대한 댓글 질문은 공식 답변이 아직 확인되지 않았다. 보수적으로 전체 실행 시간을 70분 안쪽으로 맞추는 방향이 안전하다.

- 최신 공개 오픈소스 VLM도 기준 환경에서 설치 및 실행되면 사용 가능하다.

- 참가자 질문: 70분 기준이 순수 추론만인지, 모델 로드와 이미지 로드 등 전체 코드 실행 시간을 포함하는지 문의.

작업 반영:

- 리더보드 Public 점수 최적화보다 Private/Hidden 일반화와 재현성을 우선한다.
- 모델 로드, 이미지 로드, 전처리, 추론, CSV 생성까지 전체 파이프라인 시간을 측정한다.
- A6000 48GB 단일 GPU에서 설치와 실행이 되는 모델/라이브러리 조합만 후보로 둔다.

## 2. 평가 규칙 안내

출처: [416786](공식 원문 링크 제외)

공식 게시글 핵심:

- 사용 가능 언어는 Python이다.
- 법적 제약이 없는 외부 데이터는 사용할 수 있다.
- 공개 데이터, 자체 수집 데이터, 합성 데이터, 생성형 AI로 생성한 데이터 사용은 가능하다.
- 평가 데이터셋을 원천으로 유사 문항, 지문, 선택지, 학습 데이터 등을 생성하거나 재구성하는 행위는 금지다.
- 평가 데이터셋의 정답 또는 이에 준하는 정보를 추론/활용하는 행위는 규칙 위반이다.
- 2026-05-31까지 공식 가중치가 공개된 오픈소스 모델만 사용할 수 있다.
- OpenAI API, Gemini API, Hugging Face Inference API, Together AI, OpenRouter 등 원격 서버 기반 모델 응답은 사용할 수 없다.
- 모델 가중치는 참가자가 직접 관리하는 환경에서 직접 로드해 실행해야 한다.
- 최종 답변은 생성형 LLM에 의해 생성된 텍스트여야 한다.
- 단순 룰 기반 출력, 조건문 기반 매핑, 사전 정의 정답 목록 선택만으로 구성된 최종 응답은 허용되지 않는다.
- 모델 앙상블과 다중 프롬프트는 가능하지만, 최종 제출 답변은 LLM이 후보 답변, 근거, 검토 결과를 종합해 생성해야 한다.
- 최종 추론 코드는 데이터 전처리, 모델 로드, 추론, 최종 출력 생성 과정을 포함해야 한다.
- 오프라인 환경에서 외부 API 호출 또는 인터넷 통신은 허용되지 않는다.
- 평가 데이터셋은 제출 결과 생성을 위한 추론 목적으로만 사용할 수 있다.
- 최종 채점 파일은 제출 창에서 1개를 선택해야 한다.
- 평가 종료 후 공개되는 Private 랭킹은 최종 순위가 아니며 코드 검증 및 2차 평가 후 수상자가 결정된다.

댓글 Q&A:

- 참가자 질문: 추론 시간 초과 시 실격 여부.
- 공식 답변: 시간 기준은 과도하게 무거운 모델을 제한하기 위한 참고 기준이지만, 실행 불가/모델 로드 불가/환경 재현 불가/시간 기준의 큰 초과로 정상 평가가 어렵다고 판단되면 심사 제외 또는 실격 가능하다.
- 참가자 질문: 기준 환경에서 허용되는 vLLM/transformers 버전 범위와 추론 시간 마지노선.
- 공식 답변: 기준 평가 환경에서 구동될 수 있어야 하며, `requirements.txt` 등으로 설치 및 제어 가능한 패키지 범위에서는 라이브러리 버전 조정이 가능하다. 추론 시간은 이미 제시된 기준을 따른다.
- 참가자 질문: 초과학기 학생 참여 가능 여부.
- 공식 답변: 재학증명서가 발급되면 재학생 신분이므로 가능하다.
- 참가자 질문: train 샘플과 test의 형식이 유사한데, train 샘플 기준으로 학습 데이터를 구성하면 실격인지 문의.
- 공식 답변: train 샘플은 학습용 데이터셋이 아니라 형식과 제출 구조를 이해하기 위한 1개 예시다. 입력/출력 형식을 맞추는 것은 괜찮지만, 평가 데이터셋 샘플의 세부 패턴을 분석/추정해 이에 맞춘 데이터, 프롬프트, 규칙을 의도적으로 만들면 규칙 위반이다.

작업 반영:

- 프롬프트는 평가 일반 목표인 bias-robust multimodal QA 원칙에서 설계하고, test 샘플 패턴 분석으로 문구를 튜닝하지 않는다.
- fallback, JSON 파서, unknown option 탐지는 출력 안정화 보조 로직으로 둔다. 최종 label 결정은 LLM reasoning 출력과 연결되도록 기록한다.
- 모델 후보는 공개일, 라이선스, 다운로드 경로, 로컬 실행 가능성, A6000 48GB 적합성을 함께 기록한다.
- 평가 제출 패키지는 인터넷 없이 재현되도록 모델 경로, 캐시, requirements, 실행 스크립트를 분리한다.

## 3. DAKER 평가 관련 문의

출처: [416785](공식 원문 링크 제외)

공식 게시글 핵심:

- 팀 구성은 정해진 기간 내에만 가능하고, 탈퇴 후 재구성은 아이디어 공유 방지 차원에서 불가능하다.
- 최종 파일은 Private 채점 결과가 가장 좋을 것으로 예상되는 파일을 선택한다.
- 최종 제출물을 선택/저장한 뒤 추가 파일을 제출하면 앞선 선택이 초기화될 수 있으며, 초기화 시 Public 기준 최고 순위 제출물이 자동 선택될 수 있다.
- baseline 라이브러리만 사용해야 하는 것은 아니다.
- 제출 결과물 개별 삭제는 불가능하다.
- Public Score는 평가 기간 중 실시간 최고 점수가 리더보드에 반영된다.
- Private Score는 평가 종료 후 내부 확인을 거쳐 공개된다.
- 동점은 해당 점수를 먼저 기록한 팀이 높은 순위다.
- 최종 선택 파일 외 제출물의 Private Score는 따로 계산하지 않는다.
- Test 데이터셋은 원칙적으로 볼 수 없다는 가정으로 다뤄야 한다.
- test를 학습, EDA, encoder/scaler fitting, 결측치 통계, `get_dummies`, 데이터 개수 정보 활용 등에 쓰면 Data Leakage에 해당할 수 있다.

댓글 Q&A:

- 참가자 질문: 대학원 수료생 참여 가능 여부.
- 공식 답변: 평가 기간 기준 재학생 및 휴학생만 가능하며 수료생은 불가능하다.

작업 반영:

- 최종 제출 직전에는 선택 파일이 초기화되지 않았는지 제출 탭 상태를 확인해야 한다.
- validation/EDA 코드는 test를 학습 데이터처럼 다루지 않도록 분리한다.
- 제출 CSV의 행/열 수, 인코딩, label 범위를 자동 검증한다.

## 4. 평가 데이터셋 구성 안내

출처: [416802](공식 원문 링크 제외)

공식 게시글 핵심:

- 평가 데이터셋은 오픈 벤치셋 기반 샘플과 운영진 자체 제작 샘플이 혼합되어 있다.
- Public Score 산출 샘플은 오픈 벤치셋 기반이다.
- 공개 벤치 데이터셋에 사전학습된 큰 모델은 Public Score가 쉽게 높게 나올 수 있다.
- Public Score가 높다고 Private Score도 높다고 단정할 수 없다.
- Private Score 샘플은 Public과 별도로 운영진 자체 제작 샘플로 구성된다.
- 평가 의도는 오픈 벤치셋 Public에 높은 모델을 찾는 것에 그치지 않고, 편향 대응 성능과 다양한 상황의 강건성을 검증/개선하는 것이다.
- Public Score는 참고 지표로 쓰되, 신빙성 있는 자체 검증 방법을 어떻게 구성할지 참가자가 고민해야 한다.

댓글 Q&A:

- 참가자 질문: Public에서는 이미지를 사용하지 않고 텍스트만 추론해도 점수가 거의 같아 보이는데, Private은 이미지가 실제로 필요하도록 설계됐는지 문의.
- 공식 답변: Public에서 이미지 없이 유사 점수가 나올 수 있는 것은 오픈 벤치셋 기반 구조와 대형/사전학습 모델의 익숙함 때문일 수 있다. 이 현상이 Private에서도 동일하다고 보기는 어렵다. Private은 운영진 자체 제작 샘플을 포함하며, 텍스트 패턴만으로 정답을 추론하는 접근은 본 평가에서 유효한 모델이 아니다.
- 참가자 질문: Public 리더보드가 포화되어 모델 개선 신호로 쓰기 어렵고, 자체 검증이 Private과 정렬되는지 calibration 없이 블라인드로 진행하는 설계가 맞는지 문의.
- 공식 답변: Public Score만으로 모델을 판단하거나 리더보드에 매몰되는 것을 방지하기 위해 데이터셋 구성을 안내했다. Bias 대응 성능과 강건성은 단일 점수만으로 판단하기 어렵고, Hidden 데이터셋 기반 평가도 같은 이유로 존재한다. 참가자는 Public Score를 포함한 여러 근거로 최종 평가에 일반화될 접근과 검증 방향을 모색해야 한다.

작업 반영:

- 모델/프롬프트 선택 기준을 Public Score 하나로 두지 않는다.
- text-only ablation은 진단 목적으로만 사용한다. 최종 접근은 이미지와 텍스트를 함께 쓰는 멀티모달 reasoning이어야 한다.
- local validation은 ambiguous/disambiguated 균형, 이미지 필요성, bias axis, text-only 실패 케이스를 포함해야 한다.
- Private shake-up을 기본 가정으로 둔다.

## 구현/실험 체크리스트

1. 새 모델 후보를 추가할 때 공개일이 2026-05-31 이전인지 확인한다.
2. A6000 48GB, Python 3.10, CUDA 12.4, Ubuntu 20.04에서 설치 가능한지 확인한다.
3. 원격 API, 인터넷 통신, 런타임 다운로드 의존을 제거한다.
4. test 데이터는 추론 입력으로만 사용한다.
5. prompt/data 생성 과정에 test 문항 패턴 분석이 들어가지 않았는지 점검한다.
6. 최종 label이 LLM-generated output에서 나온 것임을 raw output으로 보존한다.
7. 파싱 실패 fallback은 보조 안전장치로만 쓰고, fallback 빈도를 로그로 남긴다.
8. text-only와 image+text를 둘 다 측정하되, 최종 모델은 image+text 일반화 성능을 우선한다.
9. Public Score 상승만으로 전략을 바꾸지 않는다.
10. 제출 전 CSV 스키마, 행 수, UTF-8, label 범위, 최종 선택 파일 상태를 확인한다.
11. 전체 실행 시간은 보수적으로 모델 로드부터 CSV 생성까지 측정한다.
12. 수상권 제출물은 코드 검증/2차 평가에서 설명 가능한 구조로 남긴다.
